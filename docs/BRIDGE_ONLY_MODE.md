# Bridge-only and automatic connection modes

Mission 11 reran the standalone bridge on an isolated NeoForge server without Processia, and inspected Mekanism energy, inventory and fluid capabilities through MCP stdio. An invalid secret, mismatched endpoint, replayed request and revoked session were rejected at runtime. The `auto` fallback was also rerun on the isolated Mekanism profile and produced an authenticated bridge-only session after an explicit NeoForge rejection; see [Mission 11 report](MISSION11_FINAL_REPORT.md).

Mission 10 replayed `bridge-only` against isolated NeoForge generic, Processia and Mekanism profiles, and `auto` fallback against Mekanism. The fresh evidence is in [MISSION10_FINAL_REPORT.md](MISSION10_FINAL_REPORT.md). A generic bridge exposes public capabilities; Processia-only recipe listing and machine search still require the optional Processia adapter. The bridge never supplies a Mineflayer player.

The MCP server can use a local generic NeoForge bridge without creating a Mineflayer player. This is useful for NeoForge servers which reject vanilla protocol clients. The bridge remains opt-in, read-only, authenticated and loopback-only.

## Modes

- `bot` (default): existing Mineflayer connection and vanilla tools.
- `bridge-only`: no Mineflayer bot is created. Registry, server metadata, loaded-block, BlockEntity and capability tools can use an authenticated generic bridge. Player-dependent tools return `bot-required`.
- `auto`: tries Mineflayer first. It falls back only after an explicit NeoForge-client rejection, including the observed NeoForge 1.21.1 failure to decode `serverbound/minecraft:hello`. It requires the same authenticated generic bridge handshake as `bridge-only`.

Auto mode does not fall back on bridge authentication/configuration failures, generic connection failures, or unknown kick reasons. A fallback does not grant additional bridge privileges.

## Configuration

Configure the server bridge using the generic bridge variables from [the bridge protocol guide](universal-neoforge-bridge.md). The MCP process needs:

```text
MINECRAFT_MCP_BRIDGE_ENABLED=true
MINECRAFT_MCP_BRIDGE_URL=http://127.0.0.1:25677
MINECRAFT_MCP_BRIDGE_CREDENTIAL_FILE=<owner-only credential file generated by the bridge>
MINECRAFT_MCP_BRIDGE_MINECRAFT_VERSION=1.21.1
```

Select the mode with `--connection-mode bridge-only` or `--connection-mode auto`, or `MINECRAFT_MCP_CONNECTION_MODE`. In `bridge-only`, provide `--bridge-minecraft-version 1.21.1` (or `MINECRAFT_MCP_BRIDGE_MINECRAFT_VERSION`). The bridge client validates the credential file, loopback endpoint, protocol, server identity, Minecraft/NeoForge versions and registry epoch. It does not print the secret.

Example:

```powershell
$env:MINECRAFT_MCP_BRIDGE_ENABLED = 'true'
$env:MINECRAFT_MCP_BRIDGE_URL = 'http://127.0.0.1:25677'
$env:MINECRAFT_MCP_BRIDGE_CREDENTIAL_FILE = 'C:\private\minecraft-mcp-bridge.credentials.json'
$env:MINECRAFT_MCP_BRIDGE_MINECRAFT_VERSION = '1.21.1'
npx minecraft-mcp-server --host 127.0.0.1 --port 25665 --connection-mode bridge-only --bridge-minecraft-version 1.21.1
```

The ports above are examples for an isolated development server. Never replace the endpoint with a public or personal server without explicit authorization.

Linux/bash uses the same variables and CLI flags:

```bash
export MINECRAFT_MCP_BRIDGE_ENABLED=true
export MINECRAFT_MCP_BRIDGE_URL=http://127.0.0.1:25677
export MINECRAFT_MCP_BRIDGE_CREDENTIAL_FILE=/run/user/$(id -u)/minecraft-mcp-bridge.credentials.json
export MINECRAFT_MCP_BRIDGE_MINECRAFT_VERSION=1.21.1
npx minecraft-mcp-server --host 127.0.0.1 --port 25665 --connection-mode bridge-only --bridge-minecraft-version 1.21.1
```

The credential path must refer to the actual owner-only file created by the bridge. Do not copy the secret into a command line, shell history or MCP configuration.

## Tool availability and epochs

Bridge-only exposes the normal MCP tool catalogue but does not pretend a player exists. `bridge-status`, registry status/resolve/inspect/search, `minecraft-get-server-info`, `minecraft-get-capabilities`, `minecraft-list-namespaces`, and generic block/BlockEntity/capability inspection are usable after authenticated bridge validation. Player position, inventory, chat, movement, GUI, navigation, placement and digging require a connected Mineflayer player and fail with `bot-required`.

The bridge-only registry epoch is derived from authenticated server identity and the source registry generation, kept separate from any Mineflayer epoch. Before serving cached registry data, tools validate the bridge session. A revoked session or server restart invalidates old mappings; refresh obtains a new session and snapshot. Static `minecraft-data` names retain static provenance and are not runtime numeric-ID evidence.

| Compatibility | Tools |
|---|---|
| `bridge-compatible` | `minecraft-get-server-info`, `minecraft-get-capabilities`, `minecraft-list-namespaces`, `minecraft-search-registry`, `minecraft-inspect-block-entity`, `minecraft-inspect-capabilities`, `bridge-status`, `bridge-refresh-registries`, `registry-status`, `registry-resolve`, `registry-inspect`, `inspect-processia-machine`, `inspect-processia-capabilities` (the latter two use generic read-only inspection when the generic bridge is active). |
| `adapter-only` | `list-processia-machines`, `inspect-processia-recipes` require the Processia adapter and return explicit adapter-required errors on the standalone generic bridge. |
| `bot-required` | The 22 vanilla player tools: `get-position`, `move-to-position`, `look-at`, `jump`, `move-in-direction`, `list-inventory`, `find-item`, `equip-item`, `place-block`, `dig-block`, `get-block-info`, `find-blocks`, `find-entity`, `send-chat`, `read-chat`, `fly-to`, `detect-gamemode`, `list-recipes`, `craft-item`, `get-recipe`, `can-craft`, `smelt-item`. They fail with `bot-required`, not empty/success responses. |
| `separate GUI client required` | GUI tools require an enabled Processia client harness, a connected graphical client and an authenticated bridge link. Mission 7 verified client startup/handshake, screen inspection, framebuffer screenshots and two display sizes. Tool registration alone does not mean a GUI client is connected. |

## Troubleshooting

- `bridge-credential-file-required` / `credential-file-unavailable-or-invalid`: confirm that the bridge is running and has created its private credential file; check path and owner-only permissions without printing its content.
- `bridge-url-must-be-loopback-http`: use `http://127.0.0.1:<port>` and ensure the Java listener is bound to loopback.
- `bridge-minecraft-version-mismatch`, `bridge-server-identity-mismatch` or `bridge-minecraft-endpoint-mismatch`: the credential belongs to a different server run/configuration; refresh from the currently running bridge.
- `bridge-authentication_required`: session expired/revoked or Java server restarted. Run `bridge-refresh-registries` to reauthenticate; do not reuse old runtime IDs.
- `bridge-chunk_not_loaded`: use a position in an already loaded chunk; inspection does not load or generate chunks.
- `bot-required`: this tool needs a Mineflayer player and is not available in bridge-only mode.
- Auto mode stays in bot mode after a generic timeout or unrecognized kick: this is deliberate; diagnose the login rejection. Auto fallback is not a generic recovery mechanism.

## Known limitation

The NeoForge status ping exposes an `isModded` marker, while the login rejection may arrive either as explicit translated NeoForge negotiation text or as a socket close. Auto mode uses the marker only to decide whether to attempt a bridge connection; the authenticated handshake still validates the exact configured server identity, endpoint and versions. Generic decode errors alone are ambiguous (a vanilla server can emit one for an invalid player name) and never trigger fallback. Generic bridge-only mode does not include Processia-specific recipe/machine adapters; those tools return explicit adapter-required errors.
